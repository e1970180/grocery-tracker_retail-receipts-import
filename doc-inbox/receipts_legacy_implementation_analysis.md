## 1. Введение и цели реверса

Настоящий документ обобщает опыт, проектные решения (ADR), предметные правила и критические проблемы, выявленные в ходе разработки и эксплуатации легаси-системы автоматизированного ввода и распознавания продуктовых чеков.

Легаси-система строилась на базе связки:
* **Оркестратор:** воркфлоу n8n `Receipts` с нативными JavaScript-узлами;
* **Вспомогательные сервисы:** `agent_workers` (FastAPI на Python: рендеринг PDF в PNG через `pypdfium2`, валидация JSON Schema draft 2020-12);
* **Зрение и LLM:** мультимодальные модели через OpenRouter (классификация сетей и извлечение данных по чекам);
* **Хранилище:** PostgreSQL в локальной сети (LAN) с разделением прав по схеме RBAC.

Основная цель данного анализа — перенести все важные знания и архитектурные решения в новый проект на Python 3.14+ (`retail-receipts-import`), избежав повторения устраненных ошибок.

## 2. Бизнес-контекст и границы системы

### 2.1 Назначение (Purpose)
Семья совершает покупки в различных продуктовых сетях Хорватии и стран ЕС. Магазины применяют сложное ценообразование: многоуровневые скидки, скидки по картам лояльности (как включенные в цену, так и вычитаемые в конце), купоны на весь чек, залоговую стоимость тары и оплату бонусными баллами.

Задача модуля — принять цифровой чек (фото, PDF или сырой JSON), гарантировать защиту от дубликатов, распознать позиции, корректно вычислить **базовую** и **фактическую (эффективную)** стоимость каждого товара, свести бухгалтерский баланс ($\sum \text{товаров} = \sum \text{оплат}$) и сохранить чек в защищенное реляционное хранилище PostgreSQL.

### 2.2 Границы ответственности (Scope)
* **Входит в объем (In Scope):**
  * Прием цифровых чеков (PDF, JPEG, PNG, JSON);
  * Классификация торговой сети по логотипу/шапке чека;
  * Извлечение товарных строк, скидок, реквизитов филиала, даты/времени покупки и оплат;
  * Нормализация единиц измерения в канонический справочник;
  * Пересчет цен со скидками и математическая валидация строк;
  * Сведение бухгалтерского баланса чека с допуском копеечного округления кассового ПО ($\pm 0.01$ EUR);
  * Детерминированная дедупликация чеков;
  * Транзакционное сохранение чеков, товарных позиций и платежей в PostgreSQL;
  * Оповещение пользователей через Telegram о результатах обработки и ошибках.
* **Не входит в объем (Out of Scope):**
  * Категоризация товаров по классификатору COICOP (выполняется отдельным сервисом Resolver / Downstream pipeline);
  * Сканирование мятых бумажных чеков низкого качества (система ориентирована на цифровые чеки из мобильных приложений);
  * Мультивалютность (в текущей версии все расчеты ведутся строго в `EUR`);
  * Аналитика расходов и визуализация.

### 2.3 Пользователи и контроль доступа
В Telegram-интерфейсе реализован белый список авторизованных пользователей:
* `AlexProm377` $\rightarrow$ покупатель «Алексей»
* `n8046` $\rightarrow$ покупатель «Настя»
* `E140290` $\rightarrow$ покупатель «Алена»
* Сообщения от неавторизованных пользователей или неподдерживаемые типы файлов (видео, аудио, архивы) отсекаются на самом раннем этапе.

## 4. Каноническая схема данных и правила вычислений

### 4.1 Корневая сущность чека (`receipts`)

| Поле | Тип в БД | Источник | Описание и инварианты |
|---|---|---|---|
| `receipt_id` | `UUID` (PK) | Deduplicator | Детерминированный идентификатор чека |
| `store_brand` | `store_brand_enum` | Classifier / LLM | Нормализованное имя сети (`Kaufland`, `Lidl`, `Muller`, `DM`, `Spar`) |
| `store_branch_id` | `VARCHAR(50)` | LLM | Внутренний код филиала (`PJ5230`, `0198`, `K05F`) |
| `store_branch_address` | `TEXT` (nullable) | LLM | Физический адрес филиала |
| `purchased_at` | `TIMESTAMPTZ` | LLM | Дата и время покупки в формате ISO 8601 с таймзоной |
| `receipt_number` | `VARCHAR(100)` | LLM | Полный номер фискального чека как напечатан |
| `currency` | `CHAR(3)` | LLM | Строго `"EUR"` |
| `receipt_amount` | `DECIMAL(10,2)` | LLM | Итоговая сумма к оплате (поле «Za platiti» / «Ukupno») |
| `loyalty_card` | `VARCHAR(100)` (nullable) | LLM | Маскированный номер карты лояльности (`xxxxx8265`) |
| `buyer_name` | `VARCHAR(100)` | Контекст | Имя покупателя по Telegram username (`NOT NULL`) |

### 4.2 Товарные позиции (`receipt_items`)

| Поле | Тип в БД | Описание |
|---|---|---|
| `line_number` | `INTEGER` | Порядковый номер строки в чеке ($1..N$ без пропусков) |
| `raw_name` | `TEXT` | Наименование товара строго как напечатано на чеке |
| `quantity` | `DECIMAL(10,3)` | Количество товара ($> 0$) |
| `unit` | `store_unit_enum` | Единица измерения: `pcs`, `kg`, `g`, `l`, `ml`, `m`, `m2` |
| `raw_price` | `DECIMAL(10,2)` | Цена за единицу как напечатана на чеке |
| `raw_amount` | `DECIMAL(10,2)` | Стоимость строки как напечатана на чеке |
| `discount_amount` | `DECIMAL(10,2)` | Абсолютная величина скидки ($\ge 0.00$) |
| `is_discount_applied` | `BOOLEAN` | Флаг: включена ли уже скидка в напечатанную сумму строки |
| `discount_text` | `TEXT` (nullable) | Текст скидки с чека (`null`, если скидки не было) |
| `price_regular` | `DECIMAL(10,2)` | Базовая цена за единицу до скидки |
| `price` | `DECIMAL(10,2)` | Фактическая эффективная цена за единицу после скидки |
| `amount_regular` | `DECIMAL(10,2)` | Базовая стоимость строки до применения скидки |
| `amount` | `DECIMAL(10,2)` | Фактическая стоимость строки после применения скидки |

#### Алгоритм обогащения скидок (`ReceiptEnricher`):
Математика расчета эффективных величин зависит от флага `is_discount_applied`:
1. **Случай 1 (`is_discount_applied == true`):** Скидка уже вычтена из напечатанной суммы строки (акционная цена на полке):
   $$\text{amount} = \text{raw\_amount}$$
   $$\text{amount\_regular} = \text{raw\_amount} + \text{discount\_amount}$$
2. **Случай 2 (`is_discount_applied == false` при `discount_amount > 0`):** Напечатана базовая цена, скидка указана отдельной строкой ниже (например, скидка по купону или карте магазина):
   $$\text{amount\_regular} = \text{raw\_amount}$$
   $$\text{amount} = \text{raw\_amount} - \text{discount\_amount}$$
3. **Случай 3 (скидки нет, `discount_amount == 0`):**
   $$\text{amount\_regular} = \text{raw\_amount}$$
   $$\text{amount} = \text{raw\_amount}$$

Удельные цены за единицу вычисляются после нахождения сумм строки:
$$\text{price} = \text{round}\left(\frac{\text{amount}}{\text{quantity}}, 2\right)$$
$$\text{price\_regular} = \text{round}\left(\frac{\text{amount\_regular}}{\text{quantity}}, 2\right)$$
*Если $\text{quantity} = 0$ или отсутствует, выставляется `null`, что приводит к ошибке на этапе валидации.*

### 4.3 Оплаты (`receipt_payments`)

| Тип оплаты (`payment_type`) | Когда используется | Пример из чека |
|---|---|---|
| `card` | Оплата банковской картой | `Kartica 50,43`, `MASTERCARD`, `VISA` |
| `cash` | Оплата наличными (фиксируется сумма чека, сдача игнорируется) | `Euro EUR 50,00` (при чеке 44,37 пишется 44.37) |
| `receipt_discount` | Скидка/купон на весь чек, не привязанная к конкретной позиции | `Lidl Plus Kupon -1,00` |
| `bonus_points` | Списание накопленных баллов лояльности в счет оплаты | `Müller bodovi EUR 0,49` |
| `refund` | Зачет сданной залоговой тары (ambalaža) | `ambalaža - PET 11x0,10 = -1,10` |

*Все суммы оплат в массиве `payments` сохраняются строго положительными (`amount > 0`).*

## 5. Специфика торговых сетей и правила извлечения (Store-Specific Knowledge)

В ходе работы с реальными чеками были установлены жесткие правила для конкретных торговых сетей:

### 5.1. Kaufland
1. **Идентификатор филиала (`store_branch_id`):**
   * Извлекается из кода `PJ####` в заголовке (например, `PJ5230` $\rightarrow$ `"5230"`).
   * Обязательно сверяется со средним сегментом номера чека: формат `NNNNN/BBBB/X`, где `BBBB` — номер филиала. Должны совпадать.
2. **Двухкомпонентная сборка даты/времени (`purchased_at`):**
   * *Дата:* извлекается из URL онлайн-фискализации `porezna.gov.hr` (параметр `datv=YYYYMMDD_HHMM`, берется календарная дата `YYYY-MM-DD`). Дата из URL гарантирует отсутствие ошибок распознавания года.
   * *Время:* берется из фискальной строки внизу чека `Datum: DD.MM.YY Vrijeme HH:MM:SS` (с сохранением секунд).
   * **Критический запрет:** категорически запрещено брать дату из блока банковского терминала (`TERMINAL: ... DATUM: YY/MM/DD`), так как там используется инвертированный формат года (`26/02/05` — это 5 февраля 2026 года, а не 26 февраля 2005 года).
3. **Строки, подлежащие обязательному игнорированию:**
   * Промежуточные подытоги `Međusuma` / `Suma` — печатаются в середине длинных чеков, не являются товарами.
   * Строки `Povratna naknada` — служебные строки учета залога внутри позиций.
4. **Скидки Kaufland:**
   * Строка `Kaufland Card % -X,XX` идет сразу под товаром: базовая цена товара указана без скидки $\rightarrow$ `is_discount_applied = false`.
   * Акционные промо-цены `Štedite XX%`: цена строки уже снижена $\rightarrow$ `is_discount_applied = true`.
5. **Возврат тары:** строки `ambalaža - PET`, `amb.- staklo` оформляются как оплата `refund`.

### 5.2. Lidl
1. **Жесткое правило по скидкам (`POPUST`):**
   * Lidl **всегда** печатает в товарной строке полную базовую цену (GROSS).
   * Скидка печатается отдельной строкой строго под товаром: `POPUST XX% -X,XX` или `Lidl Plus popust -X,XX`.
   * **Обязательно:** `is_discount_applied = false`. Если ошибочно установить `true`, сумма скидки будет вычтена дважды либо исказит баланс чека.
2. **Ловушка подвала Lidl (двойной учет скидок):**
   * После строки «za platiti» Lidl печатает сводную строку `POPUST X,XX` (общая сумма экономии по чеку).
   * **Критическое правило:** эту строку **нельзя** добавлять в позиции и **нельзя** создавать для нее оплату `receipt_discount`, так как все эти скидки уже привязаны к индивидуальным товарам выше. Игнорировать полностью.
3. **Филиал и карта:**
   * Номер филиала извлекается из `IBR: 0198/...` или `PJ: 0198` (сохраняя ведущие нули).
   * Lidl не печатает номер карты лояльности $\rightarrow$ `loyalty_card = null`.

### 5.3. DM (dm-drogerie markt)
1. **Регистр имени сети в БД:**
   * В БД значение enum имеет вид `'DM'` (верхний регистр). Хотя на чеке пишется строчными `"dm"`, маппинг обязан отдавать именно `'DM'`, иначе PostgreSQL отклонит запись из-за несоответствия `store_brand_enum`.
2. **Филиал:** буквенно-цифровой средний сегмент номера чека (например, `9619/K05F/5` $\rightarrow$ `store_branch_id = "K05F"`).
3. **Отмены (`STORNO RETKA`):** при наличии строк отмены из финального списка удаляются и исходная строка, и строка отмены. Отрицательные позиции не создаются.
4. **Единицы измерения:** в сети DM все товары продаются строго поштучно (`unit = pcs`). Весовых товаров нет.

### 5.4. Müller
1. **Главная причина расхождения баланса (`Müller bodovi`):**
   * Между строкой промежуточного итога `Međuzbroj` и строкой `ZA PLATITI` может присутствовать строка:
     `Müller bodovi EUR 0,49` (оплата покупки накопленными бонусными баллами).
   * Если пропустить эту строку, сумма товаров чека окажется больше суммы оплаты по карте на 0.49 EUR, и валидация баланса упадет.
   * **Правило:** при положительной сумме на строке `Müller bodovi` обязательно создавать запись в `payments`:
     `payment_type = "bonus_points"`, `amount = 0.49`, `description = "Müller bodovi"`.
2. **Имя сети в БД:** строго `'Muller'` (без умлаута `ü`, латиница).
3. **Залоговая тара (`POVRATNA NAKNADA`):** в Müller залоговая тара при покупке пробивается отдельной строкой как обычный положительный товар (+0.10 EUR) и входит в промежуточный итог.

## 6. Важнейшие решенные проблемы и найденные грабли (Lessons Learned)

В данном разделе собраны наиболее ценные инженерные инсайты, зафиксированные в ChangeLog и ADR легаси-проекта:

### 6.1. Исключение `receipt_number` из ключа дедупликации (ADR-3)
* **Первоначальное решение:** Хэш UUIDv5 строился по формуле `store_brand + purchased_at + receipt_number`.
* **Почему сломалось:**
  1. OCR часто ошибался в сложных номерах чеков (путались символы `/`, `1`, `I`, `l`, пробелы). Из-за этого повторная отправка того же чека приводила к генерации другого ID и дублированию записи в БД.
  2. При невозможности распознать номер чека подставлялся сентинел `UNKNOWN_RECEIPT_NUMBER`. В результате разные чеки из одного магазина получали коллизии.
* **Итоговое решение:**
  * Ключ дедупликации строится строго как: `norm(store_brand) + "_" + norm_iso_utc(purchased_at)`.
  * Номер чека намеренно исключен: эмпирически доказано, что в рамках одной семьи покупки в одной и той же сети с точностью до секунды не совершаются.
  * Если сеть или дата не распознаны, в качестве аварийного tiebreaker используется telegram `file_id`.
  * *В новом сервисе на Python:* при переходе на `uuid.uuid7` для идентификации сущностей уникальный бизнес-инвариант `UNIQUE (store_brand, purchased_at)` должен быть сохранен для надежной дедупликации.

### 6.2. Ложные ошибки валидатора из-за обратного пересчета округлений
* **Первоначальное решение:** В валидаторе `IntegrityValidator` проверялось равенство:
  $$\text{item.amount} \stackrel{?}{=} \text{round}(\text{item.price} \times \text{item.quantity}, 2)$$
* **Почему сломалось:** Цена `price` сама является вычисляемой величиной ($\text{amount} / \text{quantity}$), округленной до 2 знаков. При обратном умножении на вес (например, $0.774 \text{ кг}$) двойное округление приводило к расхождению в 1–2 цента, и валидатор ошибочно браковал идеально распознанные чеки.
* **Итоговое решение:**
  * Сверка сумм должна производиться **напрямую с исходными полями чека**:
    * При `is_discount_applied = true`: ожидаемый $\text{amount} = \text{raw\_amount}$, $\text{amount\_regular} = \text{raw\_amount} + \text{discount}$.
    * При `is_discount_applied = false`: ожидаемый $\text{amount} = \text{raw\_amount} - \text{discount}$, $\text{amount\_regular} = \text{raw\_amount}$.
  * Обратный пересчет через `price` исключен.

### 6.3. Порядок нормализации единиц измерения (`NormalizeUnits` до `ValidateSchema`)
* **Проблема:** LLM часто извлекает единицы измерения на языке чека (`kom`, `komada`, `упаковка`, `paket`, `pk`, `par`). Если запустить валидацию JSON Schema до узла нормализации, валидатор отклонит документ, так как схема требует строго канонические единицы БД (`pcs`, `kg`, `g`, `l`, `ml`, `m`, `m2`).
* **Решение:** Узел нормализации единиц по словарю синонимов должен выполняться **строго до** вызова валидатора схемы.

### 6.4. Проблема стрингификации `null` в PostgreSQL (`"null"` vs `NULL`)
* **Проблема:** В n8n подстановка параметров через строковую склейку (`queryReplacement`) превращала JavaScript-значение `null` в текстовую строку `"null"` (4 символа). В результате в колонки `receipts.loyalty_card` и `store_branch_address` в базе данных вместо реального SQL `NULL` записывалось текстовое слово `"null"`. При этом JSON Schema пропускала такое значение, так как `"null"` является валидной строкой.
* **Легаси-костыль:** Оборачивание параметров в SQL: `NULLIF(NULLIF($n, 'null'), '')`.
* **Требование к новому проекту:** Использовать нативный драйвер базы данных (например, `asyncpg` или `psycopg`), где Python `None` транслируется в SQL `NULL` на уровне бинарного протокола без строковой интерполяции.

### 6.5. Обязательный fallback для `buyer_name`
* **Проблема:** Колонка `receipts.buyer_name` имеет ограничение `NOT NULL`. Если у Telegram-аккаунта не задан `username` или чек передан через API/скрипт, возникала ошибка `NotNullViolation` и транзакция откатывалась.
* **Решение:** Всегда гарантировать безопасный дефолт: `username or first_name or "UNKNOWN_BUYER"`.

### 6.6. Ограничения модели прав RBAC в PostgreSQL
* **Владение схемой:** Вся схема, таблицы, типы и функции в реальной базе принадлежат единому владельцу — `ai_developer`.
* **Двухуровневая модель доступа:**
  * Роли-пакеты прав (`NOLOGIN`): `receipt_rw`, `receipt_ro`.
  * Логин-роли сервисов: `n8n_receipt_rw` (входит в `receipt_rw`), `n8n_receipt_ro` (входит в `receipt_ro`), `nocodb` (входит в `receipt_rw`).
* **Следствие триггеров `SECURITY INVOKER`:**
  * Триггеры выполняются от имени вызывающей роли. Роли на запись (`receipt_rw`) требуются явные права `USAGE` на enum-типы, права на последовательности (sequences) и права `DELETE` на дочерние таблицы (`receipt_items`, `receipt_payments`) для корректной работы каскадного удаления чека.

### 6.7. Семантика ответов сервиса валидации схем
* В спецификации API микросервиса `agent_workers` зафиксирован важный инвариант:
  * Невалидный JSON чека возвращает **HTTP 200** с телом `{"valid": false, "errors": [...]}`. Ошибки бизнес-данных никогда не транслируются в HTTP-статусы.
  * HTTP 4xx/5xx означают сбой самого запроса (битая схема, невалидный формат JSON запроса, падение сервиса).
  * Клиент обязан сначала проверять HTTP-статус, а затем поле `body.valid`.

## 7. Технический долг легаси и рекомендации для новой реализации

При переносе логики в проект `retail-receipts-import` необходимо учесть следующие рекомендации:

1. **Единая реализация на чистом Python 3.14+:**
   * Отказаться от разрозненных JavaScript Code Nodes в n8n в пользу строго типизированных Pydantic v2 моделей и доменных сервисов.
   * Использовать стандартную библиотеку Python 3.14 (`uuid.uuid7` для сквозных трекинг-идентификаторов пачек инжеста/событий).
2. **Надежная дедупликация:**
   * Сохранить бизнес-инвариант `store_brand + purchased_at` в качестве уникального ключа отсечения дублей чеков.
3. **Прямая работа с PostgreSQL через Lan-драйвер:**
   * Исключить строковую склейку SQL-запросов.
   * Использовать транзакционный блок (`async with connection.transaction():`) для атомарной записи шапки чека, позиций и платежей.
4. **Устранение потери причин ошибок (Diagnostic Tracing):**
   * В легаси-воркфлоу при синтаксически битом JSON причина ошибки терялась из-за очистки объекта перед валидатором. В новом сервисе ошибки парсинга, валидации схемы и расхождения баланса должны сохраняться с подробным контекстом.
5. **Поддержка Human-in-the-Loop (HITL) и теневых полей:**
   * Реализовать сохранение промежуточных сбойных чеков с теневыми полями `__ERROR_{field_name}` для возможности их ручной корректировки и повторной отправки в конвейер.
6. **Тестирование на реальных фикстурах:**
   * Пополнять тестовый набор `tests/fixtures/` примерами чеков Kaufland, Lidl, DM, Müller, Spar, отражающими краевые случаи (скидки, возврат тары, баллы лояльности).
