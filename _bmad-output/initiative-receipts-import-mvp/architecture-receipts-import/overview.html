Как сервис превращает фото чека в строку в PostgreSQL

Обзор для владельца. Нормативный документ для сборки — architecture-receipts-import.md (17 решений AD-1…AD-17); здесь то же самое простыми словами.

Форма сервиса

Один контейнер на домашнем сервере, один поток. Цикл: забрать новые сообщения из Telegram → записать принятые чеки в локальную очередь → по одному обработать всё, чему пришло время → снова за сообщениями. При двух чеках в день параллельность не нужна, и без неё исчезают гонки.

flowchart LR
  FAM[Семья] -->|фото, PDF| TG[Telegram]
  SVC[Сервис импорта] -->|опрос, реакции, сообщения| TG
  SVC --- Q[(Очередь SQLite
и файлы на томе)]
  SVC -->|изображение| GEM[Gemini Flash]
  SVC -->|роль writer| PG[(PostgreSQL в LAN)]
  RES[Resolver] -->|только чтение, resolver_v1| PG

Путь одного чека

Каждый чек — задача с сохранённым состоянием. После перезапуска задача продолжает с того шага, на котором остановилась.

flowchart TD
  A[Сообщение принято,
offset подтверждён вместе с задачей] --> B[Скачать файл]
  B --> C[Проход 1: какая сеть?]
  C -->|не из списка| U[Неподдерживаемая сеть]
  C -->|Kaufland, Lidl, DM, Müller, Spar| D[Проход 2: промпт этой сети]
  D --> E[Код сети считает цены
и сверяет суммы ±0.01]
  E -->|не сошлось, попытка < 3| D
  E --> F[Готов к записи]
  F --> G[(Одна транзакция:
чек, строки, оплата, лента)]
  G --> S[Сохранён]
  G -->|та же сеть и секунда| DUP[Дубликат]
  C -->|3 неудачи| X[Отказ]
  E -->|3 неудачи| X

Что решили вы

Владелец
Очередь — локальный SQLite на томе.Пока PostgreSQL недоступен, приём продолжается. Случай «упал между записью в БД и отметкой в очереди» распознаётся по ссылке на исходное сообщение: вы не увидите «дубликат» на свой же первый чек.
Владелец
Распознавание в два прохода.Сначала только сеть, потом промпт конкретной сети. Каждая сеть — отдельный плагин: промпт, схема, правила, фикстуры. Добавление сети не трогает остальной код, и это готовит рост до 10 сетей.
Владелец
3 попытки, расхождение сумм тоже тратит попытку.Недоступность Gemini попыток не тратит: чек ждёт без срока, вы видите реакцию «в процессе».
Владелец
Telegram — свой клиент на основе telegram_core.Код эталонного пакета копируется в проект и становится нашим. Ограничение в спеке поправлено.
Владелец
Resolver читает ленту в PostgreSQL.Строка «чек сохранён» пишется в той же транзакции, что и сам чек. Resolver читает версионированные view под своей ролью и помнит свой курсор, поэтому ничего не теряет, даже если неделю был выключен.
Владелец
Алерты — только при смене состояния.Одно сообщение «сломалось» и одно «восстановилось» на каждый вид ошибки.
Владелец
Модель по умолчанию — gemini-3.8-flash.Задаётся в env; сервис логирует фактическую версию из каждого ответа.
Технически
Модель только переписывает напечатанное.Цены до и после скидки, ловушки сетей и сверку считает код, проверенный тестами на фикстурах.
Технически
Ключ дубликата — сеть + время покупки до секунды.Это уникальный индекс в БД, урок legacy. Номер чека и хеш файла в ключ не входят.
Технически
Одна сломанная задача не останавливает приём.Неожиданная ошибка оставляет задачу на месте с паузой, вам приходит алерт, цикл идёт дальше.

Развёртывание

  • git clone со sparse-checkout и compose build; один сервис и один том. PostgreSQL — существующий в LAN, в compose его нет.
  • Три роли БД: владелец схемы (только для compose run --rm … migrate), writer для сервиса, read-only для Resolver.
  • Отдельные бот, база и том для разработки; сервис не стартует при несовпадении окружения.
  • CI на каждый push: ruff, mypy strict, pytest, а также интеграционные тесты на PostgreSQL в контейнере, никогда не на проде.

Отложено

Колонки таблиц PostgreSQL, точный список полей контракта resolver_v1, нарезка длинных чеков, формулировки промптов, версия PostgreSQL на сервере. Решения откладываются до соответствующих историй; ни одно из них не может развести независимые части.
