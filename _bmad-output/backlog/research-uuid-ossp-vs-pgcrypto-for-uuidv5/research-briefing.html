Executive summary

Verdict: Use uuid-ossp (uuid_generate_v5) rather than implementing UUIDv5 over pgcrypto (digest).

  1. PostgreSQL 18 has no built-in UUIDv5: Core adds uuidv4() and uuidv7() [7], but neither PG 18 [10] nor the 2026-11-07 devel branch [11] includes a core name-based UUID generator. unverified
  2. uuid-ossp avoids custom crypto code and links e2fs (libuuid) in Debian and Alpine Docker builds: Debian PGDG [4] and official postgres:18-alpine [6] compile with --with-uuid=e2fs, avoiding the unmaintained OSSP library noted in docs [1] verified (Bookworm postgres:18 uses PGDG apt and is inferred e2fs [5] medium). In master SQL, uuid_generate_v5 is IMMUTABLE STRICT PARALLEL SAFE in C [3], and dev-database checks matched RFC 9562 [14], CPython [15], and non-ASCII UTF-8 outputs. verified
  3. pgcrypto adds custom maintenance and FIPS uncertainty: Searches found no sourced SQL recipe for UUIDv5 over pgcrypto, and sha1 behavior in digest() under FIPS OpenSSL 3 is unverified in docs [8]. unverified
Biggest caveat: Two operational items remain unverified: how uuid-ossp--1.1.sql behaves under an empty search_path and during pg_dump/restore (the script uses no schema qualification or SET search_path [3]), and whether the migration role holds database CREATE privilege to install a trusted extension [1][2].

Core landscape and the pgcrypto alternative

  • No core UUIDv5: PG 18 adds uuidv7() and uuidv4() [7] alongside gen_random_uuid() from v13 [13], while neither PG 18 [10] nor 2026-11-07 devel [11] has uuidv3 or uuidv5. unverified
  • pgcrypto properties: Trusted in PG 18, requires OpenSSL [8], and digest(text, text) is IMMUTABLE STRICT PARALLEL SAFE in pgcrypto--1.3.sql (master; bytea overload partly verified) [9]. With gen_random_uuid() in core, loading pgcrypto would serve solely to call digest() [13]. unverified
  • Missing recipe and FIPS risk: Searches found no sourced UUIDv5 SQL recipe over pgcrypto. Docs list sha1 and say OpenSSL 3 legacy provider covers old ciphers (DES, Blowfish medium), while the FIPS note covers only gen_salt() and crypt(), leaving digest(..., 'sha1') under FIPS OpenSSL 3 unverified [8]. unverified

Packaging, build lineage, and operations (uuid-ossp)

  • Privileges & control file: PG 18 marks uuid-ossp as trusted (non-superuser with CREATE on the database can install) [1] medium unverified; uuid-ossp.control (master, not REL_18) sets trusted = true, relocatable = true, default_version = '1.1' [2].
  • Function attributes & script gaps: uuid-ossp--1.1.sql (master) marks uuid_generate_v3, uuid_generate_v5, and uuid_ns_* as IMMUTABLE STRICT PARALLEL SAFE C functions (v1/v1mc/v4 are VOLATILE) [3]. The script has no schema qualification and no SET search_path [3], leaving empty-search_path and pg_dump/restore behavior untested. unverified
  • Library backend: Upstream docs warn the OSSP library is "not well maintained" [1]. Debian PGDG [4] medium-high and postgres:18-alpine [6] build with --with-uuid=e2fs verified; Bookworm postgres:18 uses PGDG apt and is inferred e2fs [5] medium.

RFC 9562 conformance, text encoding, and test vectors

Digest caveat: web fetches in rfc-conformance-r1-1.md were summarized by a small model, so source quotes are second-hand.

  • Spec & namespaces: RFC 9562 (Sections 4.1–4.2) hashes 16-byte network-order namespace + name bytes via SHA-1, taking the leftmost 128 bits and setting version (5) and variant bits [14]. Standard namespaces match across RFC 9562 [14], google/uuid [17], and uuidjs (v35.test.ts) verified.
  • Encoding & normalization: RFC 9562 specifies no encoding or Unicode normalization [14]. Python uuid.uuid5 [15] and uuidjs (TextEncoder) [16] use UTF-8; Go takes raw bytes [17]. PG's uuid_generate_v5(uuid, text) accepts text only (no bytea overload planned per 2017 thread [12] unverified), and upstream current docs are silent on encoding [19] unverified.
  • Caveats: .NET Guid.ToByteArray() uses little-endian order for the first three fields unless swapped [18] unverified. Canonically equivalent Unicode forms hash differently without app normalization low-medium unverified. Searches found no published non-ASCII UUIDv5 vector unverified.

Cross-dimension insights

Debian and Alpine PostgreSQL 18 images avoid the unmaintained OSSP library by linking e2fs (libuuid) [4][6], removing the historical reason to build custom pgcrypto SQL while keeping cross-language determinism anchored in UTF8 encoding and explicit text normalization [14][15][16].

Contrary evidence

No red-team pass ran (preset: standard, validation: normal, red_team: off). Surviving counterarguments from digests: (1) upstream PG 18 docs warn OSSP is "not well maintained" [1] (mitigated by e2fs [4][6]); (2) uuid_generate_v5 accepts text only [12][19] without encoding docs [19]; (3) uuid-ossp--1.1.sql lacks SET search_path [3].

Recommendations

  • Adopt uuid-ossp (public.uuid_generate_v5): Schema-qualify calls as public.uuid_generate_v5(...) with an explicit uuid namespace literal [14]; specify UTF-8 and unaccent/sanitize order in migrations and warn .NET and other non-Python consumers on byte order [18] and Unicode normalization [14].
  • Runner-up (pgcrypto): Only if a host forbids uuid-ossp, write a bitwise wrapper around digest(..., 'sha1') (unverified under FIPS OpenSSL 3 [8]) and validate against RFC 9562 [14] and non-ASCII Python vectors [15].
